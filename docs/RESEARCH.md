# Research and provenance

Research date: **2026-11-07**. Repository metadata was fetched with `gh api repos/<owner>/<repo>`; package versions came from the npm and PyPI registries. The manifest records the snapshot date, repository stars, latest push timestamp, license, and source links. Stars belong to whole repositories: the 22 skill entries come from four upstream repositories, and the six ECC rule packs share the ECC repository snapshot. A high star count is not an independent quality score for every skill or rule.

## Patterns adopted

| Reference | What this project adopts |
| --- | --- |
| [Awesome manifesto](https://github.com/sindresorhus/awesome/blob/main/awesome.md) | A narrow scope, short explanations of why an item belongs, and selection criteria. Popularity alone does not qualify a tool. |
| [Awesome Python](https://github.com/vinta/awesome-python) | Organize by developer tasks so readers can find a suitable tool quickly. Keep Python tooling adjacent to the agent workflows it supports. |
| [Awesome MCP Servers](https://github.com/punkpeye/awesome-mcp-servers) | Group MCP capabilities and provide direct upstream links. This project adds explicit installable/reference-only states. |
| [OpenSpec supported tools](https://github.com/Fission-AI/OpenSpec/blob/main/docs/supported-tools.md) and [installation](https://github.com/Fission-AI/OpenSpec/blob/main/docs/installation.md) | A project initialization command, explicit agent selection, repeatable updates, and native agent configuration paths. OpenSpec remains an upstream tool with its own workflow rather than copied templates. |
| [Agent Skills specification](https://agentskills.io/specification) | Keep each selected skill's `SKILL.md` and supporting directory together, retaining the native name and description. |

## Version 0.2 catalog expansion

Catalog schema 2 contains **75 entries** and **11 profiles**. Thirty-nine entries have an installation recipe: **22 skills, 6 rule packs, 9 MCP servers, and 2 MCP-to-LSP bridges**. The remaining 36 are references, including two further LSP bridges, nine native language servers, and five security scanners.

The expansion adds a reviewed subset of ECC for engineering standards, security review, Python/FastAPI/Django, TypeScript/React/Next.js, Spring Boot, Go, API design, migrations, and deployment guidance. Rule packs use explicit source-file allowlists, native language scopes, and shared-rule dependencies. They preserve upstream originals while activating a disclosed portable adaptation. See [ECC source selection and migration boundaries](ECC-MIGRATION.md).

Serena changes from a discovery-only reference in the initial catalog to a pinned, project-aware MCP launch recipe. Native language servers remain separate reference entries; security scanners remain project/CI tooling references. [LSP and security-tool documentation](LSP.md) describes setup, prerequisites, protocol boundaries, and the recorded Serena smoke result.

`starter` now includes common rules. The Python and web profiles add the appropriate language rules and selected practices; dependencies include the common layer automatically. Framework profiles narrow the loaded guidance to the selected stack. `apd profiles`, `apd list --kind rules`, `apd list --kind lsp`, `--category`, and `--installable` expose these distinctions in the CLI.

## Why some tools are reference-only

- [GitHub MCP Server](https://github.com/github/github-mcp-server) needs an authentication and tool-permission decision. Its official setup remains the entry point.
- [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp) has browser environment assumptions beyond writing a configuration entry.
- [Sequential Thinking](https://github.com/modelcontextprotocol/servers/tree/main/src/sequentialthinking) currently publishes `2.0.0` with Node.js `>=24`, verified through [npm metadata](https://registry.npmjs.org/@modelcontextprotocol%2fserver-sequential-thinking/2.0.0). It is not part of the starter runtime.
- [Anthropic Skills](https://github.com/anthropics/skills) and [Vercel Agent Skills](https://github.com/vercel-labs/agent-skills) are collections whose individual skills have different capabilities and license considerations. They are discovery sources, not bulk-install defaults.
- [uv](https://github.com/astral-sh/uv), [pytest](https://github.com/pytest-dev/pytest), [hypothesis](https://github.com/HypothesisWorks/hypothesis), [deptry](https://github.com/osprey-oss/deptry), and [pre-commit](https://github.com/pre-commit/pre-commit) belong in a project's development toolchain. They are not ready-to-register MCP servers. `deptry` in particular has to run inside the project environment to compare declared dependencies with actual imports.
- The ten native LSP references — [Pyright](https://github.com/microsoft/pyright), [Pyrefly](https://github.com/meta/pyrefly), [Python LSP Server](https://github.com/python-lsp/python-lsp-server), [Ruff](https://docs.astral.sh/ruff/editors/), [ty](https://docs.astral.sh/ty/), [TypeScript Language Server](https://github.com/typescript-language-server/typescript-language-server), [gopls](https://go.dev/gopls/), [rust-analyzer](https://rust-analyzer.github.io/), [clangd](https://clangd.llvm.org/), and [Tombi](https://github.com/tombi-toml/tombi) — require compatible toolchains and an LSP client. Their raw launch commands do not speak MCP. Ruff also remains useful as a Python lint/format CLI, and `pyright`, `pyrefly`, and `ty` are mutually overlapping Python type checkers, so a project picks one.
- [Tombi](https://github.com/tombi-toml/tombi) is the only configuration-file server in that list: a schema-driven TOML formatter, linter, and language server for `pyproject.toml`, uv, Ruff, and pytest settings. It speaks LSP, not MCP, and one Rust binary is distributed through the curl installer, Homebrew, winget, `uvx`/`uv tool install`, npm, and the VS Code, Open VSX, Zed, JetBrains, Helix, Neovim, and Emacs integrations, so the launch command depends on the client a project already has. Completion and validation come from the JSON Schema Store; nvim-lspconfig registers it for `toml` files and roots it at `pyproject.toml`. Nothing was installed and no editor session was run for this entry.
- [agent-lsp](https://github.com/blackwell-systems/agent-lsp) does speak MCP, but it is distributed as a Go binary built by its own install script or release archive. There is no registry version or dependency revision to pin here, and it needs the individual language servers installed separately, so it stays a reference next to Serena rather than a configured bridge.
- [chunkhound](https://github.com/chunkhound/chunkhound) is published on PyPI and documents a stdio MCP launch, but its server did not answer `initialize` in a fresh project within the smoke window on this host: uvx first resolved Python 3.10, whose scipy build does not load on arm64 macOS, and after pinning Python 3.12 it stalled on an outbound HTTPS request during startup. Indexing is also an explicit separate step, the database is created inside the project, and semantic search or deep research needs an embedding or LLM provider. It stays a reference until the launch check passes.
- [ripwire](https://github.com/redhat-et/ripwire) is ranked call-graph CLI and context tooling whose one-line install downloads a SHA-256-verified release binary, stages seventeen agent skills for every agent it detects, and can add a commit hook; its MCP server is a flag on that same binary rather than a registry package, and no npm or PyPI package of this name exists, so there is no launch command to pin and no handshake was attempted. It is recorded next to `code-review-graph`, `repomix`, and `codebase-memory-mcp` as code-context tooling with a CLI-first, offline, single-binary shape.
- [mcpls](https://bug-ops.github.io/mcpls/) speaks MCP over LSP in the same way, with `rust-analyzer`, `pyright`, `gopls`, and other servers in one session. It is distributed as a Rust binary through cargo, its install script, release archives, or a container image, and needs those servers separately, so it stays reference-only as well.
- [codebase-memory-mcp](https://github.com/DeusData/codebase-memory-mcp) ships a native pure-C binary through its own install script, a Homebrew formula, and a Nix flake, with npm, PyPI, and Go packages that only verify and cache that runtime for the host. The documented MCP entry points at the installed executable, so no registry launch command is recorded and the wrapper path was not exercised as a launcher. Its installer also writes rules, skills, hooks, and agent configuration, which is a broader change than writing one launch configuration.
- [Semgrep](https://github.com/semgrep/semgrep), [Bandit](https://github.com/PyCQA/bandit), [pip-audit](https://github.com/pypa/pip-audit), [OSV-Scanner](https://github.com/google/osv-scanner), and [Gitleaks](https://github.com/gitleaks/gitleaks) need project-specific inputs, scan scope, reviewed policies/rules, and CI decisions. Their official metadata, licensing, and setup links are recorded in the manifest. Installing security guidance does not execute a scanner or imply a clean result. OSV-Scanner and pip-audit overlap on Python dependencies; OSV-Scanner additionally covers other ecosystems, SBOMs, and container images, and its advisory lookups reach the OSV database over the network.
- [FastMCP](https://github.com/jlowin/fastmcp) and the [MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk) help build integrations; they are not preconfigured MCP services.

- [ai-rulez](https://github.com/Goldziher/ai-rulez) does speak MCP for configuration reports and skill serving, but its npm and PyPI packages are Go installer wrappers that fetch a native release binary, so there is no registry launch command to pin; on this host the wrapper's own download of the v5.10.0 archive timed out and retried before any handshake. It also generates files across dozens of agent targets, which the catalog's skill and rule-pack recipes do not model. It is recorded next to `skills-cli` and `awesome-copilot` as authoring and governance tooling, and [its lock file](https://github.com/Goldziher/ai-rulez/blob/main/docs/lockfile.md) is evidence for the folder layout rather than a recipe this project installs.

- [graphify](https://github.com/Graphify-Labs/graphify) is delivered as a coding-agent skill, but the engine behind it is the `graphifyy` package and the `/graphify` skill is registered by `graphify install`, which detects the assistants on the machine and writes their configuration. Copying the skill directory alone would leave graph input and query instructions with no graph engine, which is the same boundary as Open Code Review, and its local deterministic AST parsing with explained edges and no vector store is the property worth evaluating rather than a recipe this catalog can pin. Nothing was installed and no graph was built.
- [codeboarding](https://github.com/CodeBoarding/CodeBoarding) publishes a pinnable PyPI CLI (`pipx install codeboarding`, Python 3.12), but the analysis needs a configured model provider and sends code excerpts to it, so a project would depend on credentials and provider policy before the first diagram exists; `codeboarding-render` only re-renders an analysis that already exists. It is recorded as the entry that turns a codebase into architecture documentation and diagrams for review and agent context, next to the code-context tools rather than as an installable recipe. Nothing was installed and no analysis was generated.
- [MCP Context Forge](https://github.com/IBM/mcp-context-forge) does publish a uvx-launchable package, but it is a gateway that refuses to start without generated `JWT_SECRET_KEY` and `AUTH_ENCRYPTION_SECRET` values, and its stdio transport is documented for server-side use only, so a registered configuration would not answer a first call. This is the same reasoning that keeps the GitHub and database MCP servers reference-only; what it adds is federation, registry and governance in front of many servers rather than one more tool.
- [Ruler](https://github.com/intellectronica/ruler) speaks no protocol at all: `ruler apply` reads a `.ruler/` directory and rewrites the native instruction, MCP, skill and subagent files of more than thirty coding agents, and also maintains `.gitignore` for them. That is a broader, project-wide change than the catalog's copy-based rule recipes model, and it is recorded next to `ai-rulez` as the applying counterpart to its authoring and governance layer. Nothing was installed and no file was generated.
- [Open Code Review](https://github.com/alibaba/open-code-review) speaks code review rather than a protocol this catalog can register: the reviewer is a global npm CLI that needs an LLM provider and API key configured through its own interactive setup, and its skills and agent plugins are only useful once that CLI exists. Copying the skill without the engine would leave a project with instructions and nothing to run.
- [MCP Inspector](https://github.com/modelcontextprotocol/inspector) is the reference debugging client for MCP servers, not a server a project registers, and upstream publishes it on the npm `latest` tag instead of pinning a version in its own instructions, so it is recorded as the tool to use when a recipe here does not answer the handshake.
- [MCP Toolbox for Databases](https://github.com/googleapis/mcp-toolbox) does publish launchable packages (`npx -y @toolbox-sdk/server --prebuilt=postgres`), but every useful launch needs database credentials the project must supply and the custom-tool path needs a `tools.yaml`; a written configuration would register a server that cannot answer its first query. This is the same reasoning that keeps GitHub's MCP server reference-only.
- [Spec Kitty](https://github.com/spec-kitty/spec-kitty) keeps specifications, work packages, acceptance criteria, review state, and merge decisions in the repository and runs each work package in an isolated git worktree under `.worktrees/`, with lanes (`planned`, `in_progress`, `for_review`, `approved`, `done`), `spec-kitty agent tasks status`, and the loop `specify -> plan -> tasks -> next -> review -> accept -> merge`. Nothing was installed and no mission was created.
- [Cross-Code Organizer](https://github.com/mcpware/cross-code-organizer) is a local dashboard over the harness inventory itself: it reports what Claude Code, Codex, OpenCode and DSH will actually load per project (the effective set, not only the files on disk), accounts for context budget, edits Memory/`CLAUDE.md`/`SKILL.md` markdown in place, repairs duplicates reversibly, copies skills between harnesses, and scans MCP tool descriptions for poisoning with findings that link back to the server entry. It reads `~/.claude/`, `$CODEX_HOME`, `~/.config/opencode/`, `$DSH_HOME`, and discovered project directories, uploads no configuration or content, and sends only an opt-in monthly activity signal (UTC month, a rotating pseudonymous ID, its version, and a harness ID). It is adjacent to `mcp-inspector` (protocol debugging) and `mcp-context-forge` (gateway and registry) rather than a duplicate of either. Nothing was installed or launched.

## Verification boundaries

This research verifies source identity, published package availability, manifest pins, selected skill/rule directory completeness, declared setup requirements, and the protocol checks below. Native rule generation is covered by this project's adapter tests; that does not imply every upstream guidance example was executed. It does not establish a security audit, benchmark ranking, or compatibility with every version of every agent. Installer tests and release CI cover this repository's configuration behavior; users still need the selected agent, required runtimes, network access, and any upstream service credentials.

MCP top-level package versions or Git source revisions are pinned. Their transitive dependency graphs are resolved by npm/uv at launch and are not fully locked by this catalog. Serena may download additional language-server dependencies when it activates a project. A registry version or Git revision pin should therefore not be described as a hermetic runtime. Skill/rule archives are checked against an exact recorded digest; an upstream archive byte change causes a verification failure until deliberately reviewed.

## Refresh procedure

Updates are curated and pinned. Regenerating installed instructions uses the catalog bundled with the installed CLI version; it does not watch upstream projects, follow new default-branch commits, or automatically import new rules, hooks, or skills. Changing an upstream pin is a reviewed catalog change.


1. Fetch repository metadata and check that the project remains active, documented, and suitable for its category.
2. Review upstream changes and license changes; do not automatically equate a larger star count with admission.
3. For a skill or rule pack, choose a full commit, download its archive, compute SHA-256, and check the selected directories/files and root license. For rules, review scopes, shared dependencies, relative links, portable transformations, and activated instruction size.
4. For MCP or an LSP bridge, verify the exact registry version or Git revision, binary entry point, supported runtime, and documented configuration. Test the server with a compatible client before expanding support claims. Keep native LSP servers and project scanners reference-only until a separate integration is deliberately implemented.
5. Update `catalog.json`, `CATALOG.md`, this research record, and relevant migration/setup documents in the same change, then exercise preview/install/repeat-install/update/remove in a temporary project.
